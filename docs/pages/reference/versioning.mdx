# Versioning and releases

Sotto uses one semantic application release version. The root `package.json` is the single source of
truth for the release-bearing manifests managed by `scripts/version.mjs`; internal packages not
listed below keep their own package versions.

## Why one version

Desktop, web, schema, and documentation evolve as one product. A shared version makes a release tag identify one compatible snapshot and prevents the previous situation where Git, npm, Cargo, Tauri, and the changelog all reported different values.

## Which build am I looking at?

Both apps display their version and the backend they are talking to, because the version alone does
not identify a session: a 3.2.2 desktop build can point at staging, and two browser tabs can be on
different deployments. Getting this wrong means running a pipeline against the wrong Supabase
project, so neither app makes you go looking.

| Where | Shows | Source |
|---|---|---|
| Desktop | Active environment name + version, in the nav rail | The active environment, read at runtime — the desktop switches environments without restarting |
| Portal | `<Environment> · v<version>`, pinned bottom-left | Derived from the Supabase project ref in the URL the app is actually using |

Both are `__APP_VERSION__`, injected by each app's Vite config from `package.json` — so the badge
cannot disagree with the release version.

**Production is quiet; anything else is loud.** A non-production backend renders in amber (staging or
an unrecognised project) or blue (a local stack), because "I thought I was on production" is the
mistake worth interrupting. In the portal the badge is visible to staff at all times, and to
*everyone* when the backend is not production — a client looking at a staging deploy is worth making
obvious to whoever is nearby, while a build stamp on a real client's gallery is just noise.

**The portal's label is derived, not configured.** It comes from the Supabase project ref, not a
`VITE_APP_ENV`. An env-name variable is a second thing to set per deployment and its failure mode is
backwards: forget it and production reads "unknown"; worse, a staging deploy inherits a stale
"production" and reassures you about the one thing you were checking. The Supabase URL is already
correct per environment because nothing works if it is wrong. An unrecognised ref renders the ref
itself and is never labelled production. See `web/apps/client-hub/src/lib/buildInfo.ts`.

Hover either badge for the full backend URL.

## Commands

Run version commands only from the repository root:

```bash
npm run version:check
npm run version:patch
npm run version:minor
npm run version:major
npm run version:set -- 3.0.0
```

The bump commands synchronize:

- `package.json`, `desktop/package.json`, `web/apps/client-hub/package.json`,
  `packages/asset-library/package.json`, `docs/package.json`, and
  `workers/cdn-gate/package.json`;
- the matching entries in the two lockfiles, `package-lock.json` and
  `docs/package-lock.json`;
- `desktop/src-tauri/tauri.conf.json`, `desktop/src-tauri/Cargo.toml`, and the `sotto-app` package in
  `desktop/src-tauri/Cargo.lock`;
- the first changelog release heading.

When the target version has no changelog section, the script inserts one with a placeholder. Replace it with a useful release summary before committing.

## Choosing a bump

| Bump | Use when |
|---|---|
| Patch | Backward-compatible bug fix, documentation correction, operational hardening |
| Minor | Backward-compatible user-facing capability, meaningful workflow or schema addition |
| Major | Deliberate compatibility break, migration that operators/clients must coordinate |

Choose bumps based on release impact rather than commit count; the major version alone is not an
operational-maturity claim.

## Release routine

```bash
git switch -c release/vX.Y.Z
npm run version:minor
# edit CHANGELOG.md and review generated files
npm run check
git diff --check
git commit -am "release: vX.Y.Z"
git push -u origin release/vX.Y.Z
# merge its PR to staging, verify, then merge staging to main
git switch main
git pull --ff-only
git tag vX.Y.Z
git push origin vX.Y.Z
```

Version commands intentionally do not commit, tag, or push. This keeps generated changes reviewable and prevents an accidental command from publishing a release.

The version workflow checks every pull request and `main` push. On `vX.Y.Z` tags it additionally requires the tag to equal `v` plus the root package version.

## Troubleshooting

If `npm run version:check` reports drift, do not hand-edit all manifests. First determine whether the root version is correct, then run:

```bash
npm run version:set -- <root-version>
```

Review the diff before committing. If the changelog already contains a newer release, resolve that history deliberately rather than overwriting it.
