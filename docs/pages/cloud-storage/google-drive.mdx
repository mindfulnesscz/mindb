# Connect Google Drive

## Google Cloud setup

1. Select a Google Cloud project and enable Drive API v3.
2. Configure the OAuth consent screen. Use Internal for one Workspace organization; otherwise use External and add test users while the app remains in Testing.
3. Create a **Web application** OAuth client and add `http://localhost:7623/callback` exactly.
4. Copy client ID and client secret into Sotto.
5. Prefer a Shared Drive for team ownership. Copy the ID from its folder URL and grant each connecting user sufficient content permissions. Leave it blank only when personal My Drive is intended.
6. Set a slash-separated remote folder without relying on a leading slash, then Connect.

## Background flow

Google authorization uses browser PKCE plus the configured client secret and a random state. Scope is the broad `drive` scope. `access_type=offline` and `prompt=consent` request a refresh token. The same three-minute localhost callback listener used by Dropbox captures the code; token exchange currently runs from the webview.

On each file, Sotto walks every remote-path segment. It searches for a matching folder beneath the
current parent and creates missing folders. Concurrent uploads share one in-flight resolution per
path prefix, so they cannot race each other into creating duplicate same-named folders. Shared Drive
queries include `corpora=drive`, `driveId`, `includeItemsFromAllDrives`, and `supportsAllDrives`.

New files up to 5 MB upload as one multipart request (metadata + bytes); **larger files use a
resumable session** (`uploadType=resumable`) whose body is **streamed off disk natively** and never
enters the webview — see [How the bytes actually move](/cloud-storage/overview#how-the-bytes-actually-move). Before
uploading, Sotto checks for an existing same-name file in the target folder. It skips only when both
size and Drive's `md5Checksum` match a native streaming checksum of the local file; equal-size
changed content updates in place instead (media `PATCH`, or a resumable update when large). With link
generation enabled, it adds an `anyone/reader` permission and returns `webViewLink`; the permission
response is not checked before returning.

**Existence is answered from one listing per folder, not one query per file.** After the destination
tree is resolved, Sotto lists the children of every folder it is about to write into, once, and every
upload in that run reads its answer from there — a destination with 300 assets across 12 folders used
to spend 300 round trips learning what 12 could tell it. Two files of one name in a folder resolve to
the **oldest**, the same rule folder resolution uses, so two runs cannot update different copies. A
file created during the run is folded back into the listing, so a second file of the same name later
in the same run updates it rather than adding a duplicate. **A failed listing falls back to a query
per file**: a listing believed complete when it is not would read as "not uploaded yet" and put a
second copy beside the client's file.

The local checksum is also memoized — see
[Cloud destination comparison](/cloud-storage/overview#what-a-run-costs-when-its-upload-cache-is-cold).

## Tradeoffs

Shared Drives give organization ownership and consistent destination regardless of who connects.
Folder creation is convenient. Costs are broad OAuth scope, a client secret stored in the
workstation's OS keychain, API quota usage from folder and
file searches, and potentially public sharing. Google-native anonymous sharing may be blocked by
Workspace policy.
