# OAuth and token lifecycle

Access tokens authorize provider API calls; refresh tokens obtain new access tokens without repeating consent.

**Destination structure** (name, type, remote path, `minRole`, generate-link, etc.) is edited in the **web portal** and pulled into desktop via Sync. **Tokens and Google client secret** stay in the workstation's OS keychain. `client-local.json`, Supabase definitions, and client exports are credential-free.

Status is purely time-based: no token, fresh, expiring within one hour, or expired. Google access tokens typically have a one-hour lifetime, so “Expires soon” can appear immediately. The pipeline filters for the presence of an access-token string, not current expiry, and does **not** automatically refresh before upload. Use Refresh token in Settings before a run.

Refresh behavior:

- Dropbox: refresh-token POST with app key.
- OneDrive: native refresh call with client ID and tenant authority; Microsoft may rotate the refresh token.
- Google: token POST with client ID, client secret, and refresh token.

Revocation, password/policy changes, consent removal, Testing-mode expiry, or missing offline consent can invalidate refresh tokens. A failed refresh requires reconnecting.

On first load of an older `client-local.json`, desktop copies every inline provider credential into the OS keychain and rewrites the file only after all copies succeed. If keychain access fails, the old file is left unchanged and the error is surfaced. Old backups made before this migration may still contain live tokens; delete or protect them and rotate credentials after suspected exposure. Service-role and permanent R2 secrets should not be present in current exports.
