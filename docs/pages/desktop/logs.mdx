# Logs and diagnostics

Always read the section header before interpreting a symbol.

| Log | Meaning |
|---|---|
| `THUMBNAILS` green `✓` | A local sidecar was freshly created |
| `THUMBNAILS` dim `↷ skipped (exists)` | Rust found the sidecar already present |
| `CDN UPLOAD` green `✓` | R2 command returned successfully; current code logs green even when Rust content-hash-skipped the PUT |
| `CDN ORIGINALS` green `✓` | Original URL was populated; may likewise represent a hash skip |
| `CLOUD EXPORT` green `✓` | Provider call succeeded; Dropbox separately logs existing paths as dim skips |
| red `✕` | That file/operation failed; sibling jobs usually continue |

## Timings

Every section-DONE banner ends with how long that section took — `━━━ THUMBNAILS DONE — 42 created · 0 errors ━━━ in 41.0s` — and the run closes with a `RUN TOTAL` block:

```
━━━ RUN TOTAL — 3m 12s ━━━
  1. SUPABASE EXPORT   48.2s  (25%)
  2. THUMBNAILS        41.0s  (21%)
  3. CLOUD EXPORT      33.5s  (17%)
  4. CDN THUMBNAILS    12.4s   (6%)
  5. PUBLISH            9.1s   (4%)
  measured 2m 24s of 3m 12s
```

Read it as follows.

- **`RUN TOTAL` is wall clock**, measured from the moment the Run button is pressed. It covers the pre-run fetches (vocabulary, storage grant, asset levels, page-preview limit) and the post-run portal sync as well as the pipeline stages, because those are where the run's silent gaps have historically been.
- **The ranking lists top-level phases only.** A step inside a phase — the Supabase export's `plan`/`writes`/`disconnect`, one cloud destination of several — reports its own duration on its own line where it happens, but stays out of the ranking so a parent and its child cannot take two slots to say one thing.
- **`measured … of …` is the honest line.** The two numbers differ by whatever the run does that nothing times. A large and growing gap is the signal to instrument something new, not a rounding artefact.

Durations are wall clock, not CPU time: a phase waiting on the network reports the wait. That is the intent — the operator is waiting too.

## Comparing runs

Every run is appended to `run-timings.jsonl` in the app data directory, and each new run is compared against the last comparable one:

```
━━━ RUN TOTAL — 2m 5s ━━━  (-1m 7s vs previous run)
  1. THUMBNAILS         41.0s  (33%)        —
  2. CLOUD EXPORT       33.5s  (27%)    +2.1s
  3. CDN THUMBNAILS     12.4s  (10%)        —
  4. PUBLISH             9.1s  ( 7%)     new
  5. SUPABASE EXPORT     6.1s  ( 5%)   -42.1s
  measured 1m 44s of 2m 5s
  vs 07/08/2026 09:20 · 312 asset(s) · 3.2.2
```

- **`—` means unchanged.** Anything under 100 ms of movement is reported that way: below that the number is scheduler noise, and a column of `+11ms`/`-7ms` reads as signal when it is not.
- **`new` means the baseline had no such phase** — a stage that was off last time, or one that did not exist in that build. It is not an infinite regression, so it is not reported as one.
- **The last line is provenance, and you should read it.** Asset count is deliberately *not* part of what makes two runs comparable — it drifts a little every run and matching on it would reject nearly every comparison — so it is printed instead, for you to discount a comparison that is not fair.

**What counts as comparable:** the same client, the same stages enabled, and the same dry-run flag. A run with thumbnails off is not faster than one with thumbnails on, and a dry run is not faster than a real one; matching on the stage set is what stops the log claiming either. A **stopped** run is excluded on both sides — it is a partial measurement, and comparing against one would report a large fictional regression on the next full run. When nothing comparable exists, the headline and the delta column are simply omitted rather than guessed at.

The file itself is one JSON object per line — client, app version, stages, asset count, and every phase *and sub-step* with its milliseconds, not only the five that made the ranking. Reach it from **Settings → Diagnostics**, which opens or reveals it. It is capped at the most recent 500 runs.

```bash
# the five slowest phases across every run of the last week, worst first
jq -r '.phases[] | @tsv' ~/Library/Application\ Support/*/run-timings.jsonl \
  | sort -k2 -rn | head -5
```

Counters are shared across stages. `published` can include multiple destinations, so it is not a unique-asset count. `skipped` includes benign unchanged work and contributes to “completed with issues.” CDN thumbnail summary’s “no thumb” bucket means a missing local sidecar (not an inventory shortcut).

For proof, inspect the target appropriate to the phase: local filesystem for generation, R2 metadata/object URL for CDN, provider UI/API for cloud export, and Supabase row for portal state.
