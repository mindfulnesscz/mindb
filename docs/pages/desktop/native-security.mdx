# Desktop native security boundaries

## Filesystem scope

The webview can ask native commands to compare, render, or upload a local file, but naming a path
does not grant access to it. Rust canonicalizes existing paths and existing ancestors, then requires
both the requested and resolved paths to be inside Tauri's approved filesystem scope. This blocks
absolute out-of-scope paths, `..` traversal, and symlink escapes.

Approved roots are:

- Sotto's app-data directory;
- folders selected with a Tauri folder picker during this session. The pickers pass
  `recursive: true`, which is what makes the grant cover the whole subtree — without it Tauri grants
  only the folder and its immediate children, and every asset sits deeper than that;
- machine-local source, destination, vault, and creation folders read from Sotto's persisted client
  configuration. These are read at startup **and re-read once on a scope miss**, because on a fresh
  install the configuration is written after launch — at boot there is nothing yet to grant.

Use the **Browse** control when assigning a new local folder. The selection grants access for the
current session, and its persisted client entry restores that grant after restart.

Re-reading on a miss does not widen the boundary: the roots still come from Rust reading app-local
configuration, never from an IPC argument, so a caller cannot grant itself a directory by naming one.

The `fs` capability does still carry a broad `**` allow for the **JavaScript** filesystem commands —
a 3.2.1 stopgap, tracked in `planning/01_stabilize-hardening-regressions.md`. That does not widen the
native command surface: `path_policy` checks the runtime scope described above, which capability
globs do not populate.

The boundary applies to native thumbnail and document-preview inputs and outputs, R2 and Dropbox
upload sources, byte comparisons, and reveal roots. Provider credentials and request headers do not
change which local files a command may read.

## Supabase proxy and CSP

`supabase_request` accepts only HTTP(S) URLs whose origin exactly matches the active Supabase URL in
the persisted environment configuration. Scheme, host, and effective port must all match. Redirect
following is disabled so a configured origin cannot redirect API keys or authorization headers to
another host.

The Tauri CSP explicitly allows app scripts and the network origins used by Supabase, Dropbox,
Google Drive, Microsoft Graph/OneDrive, and local development. Add a provider endpoint narrowly to
`connect-src` when introducing a new integration; do not disable CSP.

## Reveal bridge

The localhost bridge at `127.0.0.1:7624` supports:

- `GET /health`, for availability checks;
- JSON `POST /reveal`, for the reveal action;
- `OPTIONS /reveal`, for the browser preflight.

Reveal requests require an exact allowed `Origin`: the production portal, staging portal, or local
portal on port 5173. Responses echo that one origin and never send
`Access-Control-Allow-Origin: *`. Request headers and the declared body are read in a bounded loop,
so a normal request split across TCP reads still succeeds while oversized or incomplete requests
are refused.

The bridge parses `.dchub.json` and compares its top-level `stable_id` exactly. Malformed manifests
and values that merely contain the requested text are ignored. Directory symlinks are not followed
during the source-tree walk.
