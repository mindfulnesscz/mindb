# Asset Pipeline

The asset pipeline is a **desktop application** (`desktop`) built with [Tauri 2](https://tauri.app/) — a Rust backend with a React/TypeScript frontend. It runs on a signed-in staff machine (**editor** or **admin**) and processes creative files for the platform.

All Supabase access uses the signed-in user's JWT under RLS. There is no service-role key on the
desktop. CDN access uses short-lived `r2-grant` credentials when the environment is provisioned;
Cloudflare scopes those credentials to the selected client's public and gated key namespaces.

## Steps, in run order

Steps 1–5 are numbered checkboxes in the app's **Tasks** panel and can each be switched on/off per run. **Scan**, **Supabase sync**, and **Version history sync** aren't checkboxes — they run automatically whenever a source folder / Supabase session is present.

**Dry run is end-to-end.** It may scan local files and read portal/provider state to build a plan,
but it does not render or copy files, update identity manifests or caches, upload/delete CDN or
cloud objects, mutate Supabase rows/tags/version history, write DAM output, or start
Stream uploads. Intended actions are written to the activity log with `[DRY]`.

**Stop is cooperative.** Work already in flight is allowed to finish; **Stop** is checked before
every new item is dispatched, so nothing further starts. Post-run Supabase, CDN reconcile, tag,
version-history and Stream work use the same stop signal, so the run is not marked complete before
that tail finishes.

**Everything bounded runs through one worker pool.** Renders, CDN uploads, page previews, cloud
uploads, Supabase row writes and the CDN prune/delete sweeps all dispatch through
`services/pipeline/pool.ts`, which keeps a fixed number of items in flight and starts the next one
the moment a slot frees. The widths are **8 for uploads and renders, 4 for deletes** — a delete
destroys an object and the lists are short, so it gets the narrower lane.

The width is not the interesting part; the *scheduling* is. These stages used to run as chunked
barriers — eight started, then all eight waited for the slowest before the next eight began — so one
500 MB video or one 400-page deck held seven slots empty for as long as it took. Page previews had a
second version of the same problem: documents ran strictly one at a time with their pages eight-wide
inside, so a two-page deck used two of eight slots. Nothing about **what** is uploaded, deleted or
skipped changed with any of this, and no width was raised.

### Scan

`scanAllAssets` walks the configured source folder looking for folders named `OUT` (configurable — the naming convention settings default to `[03] OUT`) and collects every publishable file inside them (skipping each folder's `thumbnails/` artifacts and `versions/`, which is handled separately by Version history sync). This file list feeds every step below — nothing after this point re-scans the disk.

The walk composes its paths in JavaScript (`services/pipeline/paths.ts`), not through
`@tauri-apps/api/path`. Those calls look like string helpers but each one is an IPC round trip to
Rust, and the scan, publish, collect and DAM walks call them **once per directory entry** — a few
thousand bridge crossings per run to concatenate strings. The replacements are pure functions
producing byte-identical results; `.` and `..` are deliberately *not* resolved, because
canonicalisation belongs in Rust behind the path-policy scope check. Genuinely platform-specific
lookups such as `appDataDir()` still go through the real API.

### 1 — Generate thumbnails

For each collected asset, the Rust backend renders a WebP thumbnail (Office documents via bundled LibreOffice, PDFs via bundled PDFium, images directly) at the configured width/quality. Skipped for file types that don't support thumbnailing. Every output goes into a `thumbnails/` folder beside the assets it serves — see [thumbnail generation](/desktop/thumbnails) for the layout and for how a pre-3.2.2 library is migrated into it. Raster thumbnails record the source size + mtime and render settings in a hidden manifest; an existing WebP is reused only while that fingerprint still matches. Document thumbnails and page previews use the equivalent `.pages.json` fingerprint.

### CDN upload

Runs only when thumbnails are enabled **and** the Control API grant succeeds (`r2-grant`). Uploads
each thumbnail and original to Cloudflare R2 under `{client_id}/thumbnails/` or
`{client_id}/originals/` on the public tier, or `{effective_level}/{client_id}/…` on the gated tier.
The temporary credentials carry matching Cloudflare `prefixes`, so another client's key is denied
independently of the desktop's key-building logic.

**Only the highest version uploads.** When several version files of one asset sit in the same folder (`v0-3-7` next to `v0-3-8`), only the highest per base+extension is eligible — they all share one version-stable object key, so uploading more than one would make them overwrite each other every run. The log reports older versions excluded from CDN.

**Browser cache busting.** Object keys are version-stable (same path after a content bump), so public URLs include `?v=<content-hash>` and uploads set long-lived `Cache-Control`. When bytes change, the gallery URL changes and browsers fetch the new image without a hard refresh.

**Skip mechanics (fast path first):**
1. One `ListObjectsV2` sweep per prefix at phase start builds an existence manifest — no per-file HEAD/LIST requests.
2. A local upload cache (mtime + size + sha256, per machine) skips unchanged files with zero network calls; the cached public URL (with `?v=`) is still recorded so the Supabase sync never sees a gap.
3. On a cache miss, the Rust backend hashes the file and compares against the caller's cached hash or the object's `x-amz-meta-sha256` — content must differ for an actual upload to happen.

Stable-identity clients key every upload by the manifest pair, never by filename: public objects use `{client_id}/{kind}/{stable_id}/{child_id}{ext}` and gated objects add `{effective_level}/` in front. `kind` is `thumbnails`, `originals`, or `pages`; page objects continue with a zero-padded page name. Files differing only by extension get distinct child IDs. A stale-sibling cleanup removes an old original when a version bump changes its extension — but never a key claimed by another file in the same run.

After the current-level object is confirmed, the upload prunes that asset's thumbnail, original, and page objects from every other access-level prefix. This reclaims the reversible source copies left by `cdn-reconcile` and, on a demotion, closes the old wider address. The delete set is bounded to the current `(stable_id, child_id)`; a thumbnail or original still referenced by another live row (for example, a gallery parent sharing its first child's media) is retained and logged. Dry runs report the sweep without deleting, and inventory/delete failures leave the object for a later run.

This is per-run self-healing, not bucket-wide garbage collection. It covers only identities touched
by the desktop run. Objects belonging to hard-deleted rows or clients that never run the desktop
again are handled by the dry-run-first bucket collector, available to super admins in web **Admin →
CDN GC**, desktop **Settings → CDN garbage collection**, and manually through
`scripts/gc-cdn-objects.mjs`. The temporary desktop grant remains too
narrow for a full-bucket diff; the Admin Edge Function and CLI obtain separately scoped operator
credentials. See [CDN garbage collection](/operations/cdn-garbage-collection).

### 2 — Distribute packages

Finds folders matching the configured package prefix (e.g. `📦` or `[00] 📦`). These are **pickup anchors**: Collect fills each one from **sibling and nested** `OUT` folders under the same parent (including migrated `Name __hash/OUT` assets). Other package folders are skipped so anchors don't harvest each other.

Highest version only. Package folders become a **hard mirror of live OUT**:
- Files no longer present in OUT (or superseded by a higher version) are **deleted** from the source package — not `🚫`-disconnected. Disconnect renaming is only for publish **targets**, where live links may still exist.
- **Render artifacts are never kept** in source packages. A `thumbnails/` folder that somehow reached one is purged as a unit, directory included.

Migrated `Name __hash` asset folders are **not** package anchors (even with `.dchub.json`); destination export still publishes their OUT via the normal folders walk.

Copy decisions are **metadata only** (`isUnchanged`): same size, and a destination at least as new as
the source, counts as unchanged. Neither file is opened.

That is deliberate and it must stay that way. Source trees live in cloud storage — Dropbox through
the macOS File Provider — where online-only files are dataless placeholders and **any** read forces a
full download. A byte-for-byte comparison used to sit behind the stat gate, and because `copyFile`
does not preserve mtime the destination was always newer, so the gate never short-circuited: every
no-change export read the entire library and pulled every online-only file onto disk.

**The accepted trade-off is the restored-backup case.** A same-size content swap whose mtime went
*backwards* — restoring an older file over a newer one — now reads as unchanged and is skipped. Repair
it by touching the sources or deleting the target copies. Re-running is otherwise safe.

### 3 — Export to destinations

Resolves the checked **local** destination’s machine path (falling back to `settings.targetFolder`). Shape comes from `exportLayout` + optional `includePackages`. Publish/export always keeps **highest version only** (one file per base+extension).

- **`folders` (default):** mirrors the source tree looking for `OUT`, publishes contents (filenames translated), recurses otherwise. Stable-identity hash suffixes (` __a1b2c3d4`) are stripped from folder names. Package folders next to OUT are skipped here unless packages are included.
- **`flat`:** all publishable OUT files into the target root (no nesting).
- **`includePackages` (with folders):** first **refreshes each source package from sibling OUT** (same mirror rules as Distribute), then copies those live files into the target at their **nested source-relative paths**. Package filenames are translated. Never dumps packages alone at target root.

Orphan handling on the **target**:
- Outside package folders: rename with a `🚫` prefix (visible, reversible where live links may still exist).
- Inside `📦` package collections: **hard-delete** stale files (older versions, renamed tags, prior `🚫` marks). Pickup mirrors must stay exact.

Reconciliation only trusts source subtrees that were read successfully. A permission error,
unmounted volume, or other failed directory read is different from a genuinely empty folder: the
matching target subtree is protected for that run, and none of its files are renamed or deleted.
An unreadable target subtree is protected too, because entries that cannot be enumerated cannot be
classified as stale. Refusals are logged through the same destructive-stage guardrail used by
portal/CDN cleanup.

Source packages never use `🚫`.

### 4 — Cloud export

For each cloud destination with a valid OAuth token:

- **`folders`:** uploads collected OUT assets, preserving folders under OUT (highest version only).
- **`flat`:** dumps files into `remotePath`.
- **`includePackages`:** refreshes source packages from OUT, then uploads package files under their nested relative paths.

Sharing links (when `generateLink`) are keyed by `(stable_id, child_id)` and later written to
Supabase for the portal. Equal filenames in separate packages cannot overwrite each other's links.
An existing remote file is skipped only when both its size and its provider content hash match the
local file — Drive's `md5Checksum`, OneDrive's `quickXorHash` — each computed natively and reused
across destinations and runs. A destination's mtime+size cache short-circuits all of that; what it
costs when that cache is **cold** is described in
[Cloud destination comparison](/cloud-storage/overview#what-a-run-costs-when-its-upload-cache-is-cold).

**Google Drive folder resolution is race-safe.** Drive addresses folders by id, not path, and accepts
several folders with one name in the same parent — so uploading 8-wide into a tree that does not
exist yet used to create up to eight copies of every level. The destination tree is now resolved once
before the concurrent batch starts, concurrent callers for one path segment await a single shared
find-or-create, and when several same-named folders already exist the **oldest** is chosen
deterministically so every run converges on the same folder. Duplicates that are found are reported
in the run log; merging the ones already in a client's Drive is a manual, preview-first action on the
destination — see [Google Drive duplicate folders](/operations/gdrive-dedupe).

### 5 — Publish to DAM

Despite the name, this step doesn't touch Supabase or the CDN — it generates the human-readable Obsidian vault: one markdown note per asset with inherited taxonomy tags, regenerable on every run. `_X` canvases are written flat under `05 DAM/`. See [Obsidian DAM output](/desktop/obsidian).

### Supabase sync

Always runs after the steps above, if a Supabase config is present for the active client. Assets are matched by **folder-based stable identity**: an 8-hex-char hash suffix on the package folder (` __a1b2c3d4`) plus a per-folder `.dchub.json` manifest mapping individual files to a stable child ID, with SHA-256 content-hash matching as a fallback for renamed files. That pair is immune to filename and taxonomy renames. Stale rows are **soft-marked `disconnected`**, never deleted, so ratings/comments/history stay attached — see [Stable asset identity](/desktop/identity).

An asset in a folder with no hash suffix has no identity to sync by: it is reported as an error and skipped. Create packages through the Vocabulary screen so they are born with one.

**Rows are written one request each, eight at a time.** Every row is its own `PATCH` (existing) or
`POST` (new) — never a bulk upsert, because `PATCH` leaves omitted columns untouched and that is what
keeps the pipeline from overwriting portal-owned values like `perm`. What is concurrent is only the
waiting: parents and singles are written first, then children once every parent uuid is known, and
readme.md files alongside. The parent→child barrier is load-bearing; a child needs its parent's
resolved uuid. A failed row is logged and counted and does not stop its siblings, and **Stop** halts
further dispatch while letting requests already in the air finish.

**A package's `readme.md` is regenerated every run but written only when it changed.** Its content is
a pure function of the row it describes — no timestamp — so a run over unchanged data writes nothing
and reports `readme.md: 0 updated · N unchanged`. That matters because these notes live in the
client's synced source folder, one per package: an unconditional write handed Dropbox the whole
library to re-upload after every run. The comparison is against the file on disk rather than a record
of what the last run wrote, so an edited or deleted readme is still healed by the next run.

Because a long run can cross the one-hour access-token expiry, a `401` is retried once with a
force-refreshed token. That refresh is **single-flight**: eight concurrent writes hitting `401`
together trigger one `refreshSession()`, not eight. GoTrue rotates the refresh token on use, so
concurrent refreshes would present an already-spent token and can trip reuse detection — revoking the
session that had just been renewed.

This step also cleans up R2 thumbnails, originals, and known page-preview objects for assets no longer present on disk. Exact keys are rebuilt from `(stable_id, child_id)`, the row's effective access level, and the shared `@sotto/domain/assetStorage` rules, so public and gated buckets use the same addresses as upload. Any key still referenced by an active record is protected (including a gallery parent's shared thumbnail). Only rows successfully marked `disconnected` contribute deletion keys. Row disconnects and object deletes pass a blast-radius check: above the small-deletion floor, removals cannot exceed rows written unless the operator selected **Allow large deletions**.
If any source subtree failed to scan, row disconnects are refused outright; a partial source view is
not evidence that the absent identities left disk.
If the initial existing-row read fails, planning and all writes are aborted as well; an empty/unknown
read result is never treated as permission to insert every local asset again.

The portal remains authoritative for tag labels and groups. Local unpublished leaf edits may be
upserted, but pass-3 tag deletion is refused when the local vocabulary is dirty/stale. Deletion is
allowed only from an explicitly fresh portal-synchronized vocabulary, and then it passes the same
write-to-delete blast-radius check as row disconnects. This prevents a cached vocabulary from
deleting tags that were added in the portal. Shortcode edits affect names generated after the
desktop refreshes its vocabulary; existing filesystem names are not rewritten automatically.

### Version history sync

Scans each asset's `versions/` subfolder and upserts the `version_history` table: the current version is marked `Active`, older ones `History`; versions removed from disk are marked `Disconnected`; assets removed entirely are marked `Removed`.

## CDN URLs and spaces

Asset filenames often contain spaces (e.g. `Sealing Pitch Deck v3.pdf`). CDN URLs are stored with literal spaces in the database. The web app applies `encodeURI()` when using these URLs in the browser to produce valid percent-encoded URLs.
