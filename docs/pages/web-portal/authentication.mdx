# Web authentication

> This page covers the **email** path. The portal also offers **OAuth sign-in with Microsoft, Google, and GitHub**, which is preferred for corporate users — provider apps, the per-environment credentials, and the redirect/callback rules all live in [Authentication](/auth). Provisioning is identical either way: OAuth returns a verified email, so the same trigger and domain whitelist described below apply. The desktop app is email-only.

Sotto uses Supabase email magic links through the `signInWithOtp` API. Before sending a link,
`check_email_auth` categorizes an address as staff, returning, whitelisted, or unknown. Root staff
sign-in and client-portal sign-in use this result differently. The staff branch includes editor,
admin, and super admin profiles. Unknown portal users can submit descriptive profile metadata, but
tenant access never comes from caller-supplied signup metadata.

On first authentication, the database trigger creates the profile and checks the verified email
domain against client whitelists. Without a match, the user remains `public` until an administrator
assigns access. Subsequent logins do not rerun first-user assignment automatically — including a
sign-in through a *different* provider, which GoTrue links into the existing user rather than
creating a new one. See [One user, many identities](/auth#one-user-many-identities).

A failed return from either path (expired link, provider denial, a `?code=` whose exchange is
refused) signs the browser out locally and renders the sign-in surface with the reason. It never
falls back to a previously stored session — see
[Returning from a redirect](/auth#returning-from-a-redirect) for why that needs saying.

The email first opens the inert `/auth/confirm` route. That page does not spend the token on load;
only its **Continue signing in** button constructs the Supabase verification URL. This protects the
link from Microsoft Safe Links and similar prefetch scanners. Supabase then redirects to the current
origin or supplied portal URL, so the Site URL and allowed redirects must include every deployed
origin/path. The template, hosted rollout order, desktop callback, and verification procedure are
documented in [Authentication → Scanner-safe confirmation](/auth#scanner-safe-confirmation).

Security note: domain whitelisting is automatic membership, not proof of a particular person’s authorization beyond control of that domain mailbox. Use narrow client domains and manual review for agencies, free-mail domains, or shared domains.
