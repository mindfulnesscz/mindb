# Portal administration

The root route is the staff landing. Without Supabase configuration it renders a locked state; with
configuration it requires an authenticated editor, admin, or super admin profile. Editors navigate
client cards. Client forms (admin and super admin) manage name, initials, accent, logo (CDN upload or
URL), `dimension_labels`, site, slug, portal background, domain whitelist, the **tags** tree, and
**export destinations**.

Users load via `get_all_profiles`; administrators change role and access through `update_user_access`
(member client picker, editor `client_members` checkboxes). Portal and desktop staff sign-in accepts
editor, admin, and super admin profiles.

Super admins also see two maintainer tabs:

- **Diagnostics** groups application errors and controls error notifications. Messages can contain
  cross-client asset names and paths.
- **CDN GC** analyzes both R2 buckets against every asset row. Execution requires a fresh matching
  plan, an exact typed object-count confirmation, and an additional production confirmation. It
  returns deletion and post-delete verification reports. See
  [CDN garbage collection](/operations/cdn-garbage-collection).

Both tabs are hidden from other roles and enforce the super-admin check again at their data/function
boundary.

### Tags and destinations in the client drawer

After selecting a client:

1. **Tags (source of truth)** — parent groups, leaf tags, JSON import/export, dimension labels. See [Taxonomy](/data-model/taxonomy).
2. **Export destinations** — delivery targets, `minRole`, portal visibility, Reveal-in-Finder flag. Desktop only connects OAuth after Sync.

Operator-oriented flow: [Tags and export destinations](/getting-started/tags-and-destinations). Also [Admin dashboard](/admin) and [Platform division](/getting-started/platform-division).
