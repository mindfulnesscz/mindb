# Authorization model

| Capability | public | member | editor | admin | super_admin |
|---|---:|---:|---:|---:|---:|
| View public permission | ✓ | ✓ | ✓ | ✓ | ✓ |
| View guest permission | ✓ | ✓ | ✓ | ✓ | ✓ |
| View client permission | — | Own client | ✓ | ✓ | ✓ |
| View internal permission | — | — | ✓ | ✓ | ✓ |
| Rate visible assets | ✓ | ✓ | ✓ | ✓ | ✓ |
| Read comments | — | ✓ | ✓ | ✓ | ✓ |
| Write comments / approvals | — | — | ✓ | ✓ | ✓ |
| Download | Released visible | Approved/published | Any visible | Any visible | Any visible |
| Set status | — | — | ✓ | ✓ | ✓ |
| Control asset permission | — | — | ✓ | ✓ | ✓ |

For members, `canViewAsset` additionally checks that the asset belongs to the client currently being viewed. Editors, admins, and super admins can switch clients. `public` is also the fallback role while a configured user profile is missing/loading.

These TypeScript checks express product behavior, not a security perimeter. Every table, view, storage URL strategy, and RPC must enforce equivalent or stricter rules in Supabase. Public R2/provider bearer URLs cannot be revoked merely by changing a database role.

Profile self-service is deliberately narrower than table-level `UPDATE` access. A signed-in user may edit benign fields on their own row, such as name, initials, company, country, and industry. The `profiles: own update` RLS policy freezes `role`, `client_id`, and `can_create_clients` to their stored values. Administrators must change those fields through the security-definer `update_user_role` or `update_user_access` RPCs, which enforce the admin and super-admin delegation rules. The broad API grants only make the table reachable through PostgREST; RLS remains the security boundary.
