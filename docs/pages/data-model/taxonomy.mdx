# Taxonomy

Internal tag dimensions are always **entity**, **angle**, and **format** (machine keys). Per-client **display names** live in `clients.dimension_labels`.

**Source of truth** is `public.tags`. For the full edit/sync workflow (portal vs desktop), start with [Tags and export destinations](/getting-started/tags-and-destinations).

## Where to edit

| What | Who | Surface |
|---|---|---|
| Dimension labels | Admin | Portal client drawer |
| Parent groups (no `shortcode`) | Admin / editor | Portal **Tags** only |
| Leaf tags (have `shortcode`) | Admin / editor | Portal **Tags**, or desktop Vocabulary + Sync |
| Filename tokens in use | Operators | Must match leaf shortcodes — renaming a shortcode does not rename files by itself |

Desktop Vocabulary **Sync** publishes dirty **leaves** then reloads from the DB. It never creates parent groups. Parent choice on desktop is a select of groups already in the portal.

## Import / export JSON

Templates are **local JSON files** (not rows in the database). On create client, optionally attach a file; on an existing client use **Import from JSON** or **Export JSON** in Tags.

Sample file in the portal app: `web/apps/client-hub/public/taxonomy.sample.json`.

```json
{
  "version": 1,
  "dimension_labels": { "entity": "Entity", "angle": "Angle", "format": "Format" },
  "nodes": [
    { "key": "entity.group", "dimension": "entity", "name": "Group", "parent_key": null },
    { "key": "entity.group.leaf", "dimension": "entity", "name": "Tag", "parent_key": "entity.group", "shortcode": "Sam" }
  ]
}
```

- **`key`** — stable identity; also used as the Obsidian tag on desktop export
- **`parent_key`** — tree grouping: nodes **without** `shortcode` are **parent groups** (portal-managed); leaves have a `shortcode`
- **`shortcode`** — filename token (leaves only)

Parse/validate/import: `taxonomyImport.ts` (`parseAndValidateTaxonomyJson`, `importTaxonomyToClient`). Export rebuilds the same document from the live DB (`buildTaxonomyDocument` / **Export JSON**). Desktop loads shortcoded tags from the DB for filename parsing and groups them by parent.

Renaming a leaf’s **display name** on the portal also rewrites that label on the client’s asset rows
(`name`, `entities` / `angles` / `formats`, `tags`) so the gallery updates without waiting for a
desktop run. A shortcode edit affects filenames generated after desktop vocabulary sync; existing
files are not renamed automatically. Editable labels are sanitized to a single cross-platform path
segment before export-name translation, so separators and traversal-only segments cannot escape the
chosen output folder.

See [Platform division](/getting-started/platform-division) and [Naming and vocabulary](/desktop/naming).

## A tag can never be its own parent

`parent_id = id` carries no information: it cannot render in the filter tree, cannot be expressed as
a `parent_key`, and makes any ancestor walk non-terminating. It is refused in three places, because
the failure it caused surfaced a long way from its cause:

| Guard | Where |
|---|---|
| Desktop sync will not write it — the tag is left ungrouped and the run log says so | `desktop/src/services/supabase/tagSync.ts` |
| Export will not emit it — the node is written with `parent_key: null`, with a console warning naming the rows that still need fixing | `taxonomy/build.ts` |
| The database rejects it outright, including a manual SQL edit | `tags_parent_id_not_self` |

**What went wrong before those existed.** Pass 1 of the desktop sync resolves a parent group by
*name* (`dimension::name`); pass 2 finds the row to update by *key or shortcode*. Nothing connected
the two, so both could land on the same row — a keyed, shortcode-less group whose name is also the
leaf's `parentGroup` — and the sync patched that row to be its own parent. The export then mirrored
it faithfully into a file the portal's own importer refused:

```
node "format.document" cannot parent itself; cycle detected involving "format.3d"
```

Read that message as **"these rows are wrong"**, not "this file is wrong" — the exporter was
reporting the database accurately. Children of a self-parenting node are reported as cycles too;
they are collateral, and fixing the parent clears them.

Deeper cycles (`a → b → a`) are **not** caught by the constraint — a `CHECK` sees one row at a time.
The write paths prevent them and `validateTaxonomyDocument` detects them, which is why an export
breaks a cycle at the edge that closes it rather than shipping a file that cannot be re-imported.

To repair an already-exported file by hand, set the offending `parent_key` to `null`; a self-parent
has no intended value to recover.
