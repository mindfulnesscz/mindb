# Roles & Permissions

## Role hierarchy

```
super_admin
  └── admin
        └── editor
              └── member
                    └── public
```

| Role | Who | Description |
|---|---|---|
| `super_admin` | Platform owners | Full staff access. Can manage admins, create/delete clients, and delegate client creation. |
| `admin` | DC Collective — administrators | Manages existing clients, users below admin, and assets. May create clients only when a super admin grants `can_create_clients`. |
| `editor` | DC Collective — creatives | Runs desktop pipeline on assigned clients; browses portals as staff. Client/identity CRUD is admin on web. |
| `member` | Approved client contacts | Portal gallery for their client; rate assets and read comment threads. **No desktop access.** |
| `public` | Signed-in users without client/staff access | Can view released public and guest-level assets. This is also the temporary application fallback while a profile loads. |

An anonymous visitor has no profile role. RLS handles that actor separately from a signed-in `public` profile.

## Role type (code)

Defined in `packages/asset-library/src/types.ts`:

```ts
type Role = 'public' | 'member' | 'editor' | 'admin' | 'super_admin'
```

## Asset permission levels (separate from role)

Each asset has a `perm` field controlling intended visibility. Lifecycle gates it independently:

```text
effective_level = status in (approved, published) ? perm : internal
```

RLS authorizes row discovery from `effective_level`, and the same level is encoded in the object key used by `cdn-gate`. This is separate from the user's profile role.

| `perm` | Visible to |
|---|---|
| `public` | Everyone, including anonymous visitors, once approved/published |
| `guest` | Any signed-in user, once approved/published |
| `client` | Members of the owning client and staff, once approved/published |
| `internal` | Staff only |

Note: the `perm` field uses the string `'client'` (not `'member'`) — this is intentional, it is an asset visibility level not a user role name.

| Action | public | member | editor | admin | super_admin |
|---|---|---|---|---|---|
| View released public/guest assets | ✓ | ✓ | ✓ | ✓ | ✓ |
| View released client assets | — | Own client | ✓ | ✓ | ✓ |
| View internal/unapproved assets | — | — | ✓ | ✓ | ✓ |
| Rate visible assets | ✓ | ✓ | ✓ | ✓ | ✓ |
| Write comments / approvals | — | — | ✓ | ✓ | ✓ |
| See view/download counts | — | — | ✓ | ✓ | ✓ |
| Edit existing clients | — | — | — | ✓ | ✓ |
| Create clients | — | — | — | If delegated | ✓ |
| View all users | — | — | ✓ | ✓ | ✓ |
| Change member/editor access | — | — | — | ✓ | ✓ |
| Grant admin/super-admin roles | — | — | — | — | ✓ |
| Desktop pipeline | — | — | ✓ | ✓ | ✓ |

## Where roles are stored

Roles are stored in `profiles.role` — a `text` column in Supabase (Postgres). Tenant assignment is `profiles.client_id`, while delegated client creation is `profiles.can_create_clients`.

Signed-in users may update benign fields on their own profile, such as name, initials, company, country, and industry. The `profiles: own update` RLS policy requires `role`, `client_id`, and `can_create_clients` to remain equal to their stored values, so direct PostgREST self-promotion or tenant reassignment fails.

Use the web **Users** tab for privileged changes. It calls the security-definer `update_user_access` RPC (role, member client, editor client memberships, and the delegated creation flag); `update_user_role` is the narrower role-only RPC. Both enforce admin checks, and only a super admin can grant admin/super-admin roles or client-creation authority. The table-wide API grant only makes `profiles` reachable through PostgREST — RLS is the security boundary.

## Creating staff accounts

There is no self-service sign-up for `editor`, `admin`, or `super_admin`. The flow is:

1. The person signs in via the root `/` admin page (or portal → admin if already staff).
2. A profile is auto-created, often as `public` (or `member` when OTP carries portal `client_id` / domain whitelist).
3. An admin promotes and assigns member/editor access on the **Users** tab. A super admin is required for admin-level grants.

## Editor portal access

Editors sign in at the root `/`. If the system has only **one client**, they are automatically redirected to that client's portal. If there are multiple clients, they see the admin dashboard and choose which portal to open.

Once inside a portal, editors see an admin navigation bar (not the member-facing header) and have access to all assets regardless of permission level.
