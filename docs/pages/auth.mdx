# Authentication

The portal offers **OAuth sign-in (Microsoft, Google, GitHub)** plus **email magic link / OTP** as a fallback — no passwords anywhere in the system. OAuth is preferred for corporate users: it avoids the email step entirely, so link-scanners like Microsoft Safe Links can't consume a one-time link before the user clicks. The desktop app remains on magic link.

## OAuth providers

The portal sign-in shows **Continue with Microsoft / Google / GitHub** above the email option. Provisioning is identical to the email path: OAuth returns the user's verified email, so the domain-whitelist trigger below still maps them to a client and role. A first-time OAuth user on a non-whitelisted domain lands as `public` and is assigned by an admin. OAuth can't carry a portal `client_id` into user metadata, so whitelist matching is by email domain.

The Supabase callback URL is the redirect URI for every provider. It is **one per Supabase project**, so there are three — local, staging, production — and none of them is a portal domain:

| Environment | Redirect URI to register with the provider |
|---|---|
| Local | `http://localhost:54321/auth/v1/callback` |
| Staging | `https://<staging-ref>.supabase.co/auth/v1/callback` |
| Production | `https://<prod-ref>.supabase.co/auth/v1/callback` |

The two hosted refs are committed in `scripts/environments/staging.public.env` and `production.public.env`.

**Local is `localhost`, not `127.0.0.1`.** `auth.external_url` in `supabase/config.toml` is pinned to `localhost` on purpose — Entra rejects a raw IP on a **Web** redirect URI — and that pin is what GoTrue uses to build the `redirect_uri` it sends to the provider. Register the IP form and Microsoft answers `AADSTS50011` (redirect URI mismatch).

Confirm the portal origins are in **Auth → URL Configuration → Redirect URLs** (e.g. `https://hub.disruptcollective.com/**`).

### Microsoft (Entra ID)

Use a **multi-tenant** app so any client organization can sign in. This can be the *same* Entra app used for SharePoint uploads — see [Microsoft & SharePoint setup](/cloud-storage/microsoft-setup).

1. Entra ID → **App registrations → New registration**; supported account types **Accounts in any organizational directory (multi-tenant)**. `/common` (below) also admits personal Microsoft accounts — use `/organizations` to exclude them.
2. Add a **Web** redirect URI for **each** environment's Supabase callback — one app can hold all three.
3. **API permissions** (Microsoft Graph, delegated): `openid`, `email`, `profile`, `User.Read`. Entra returns no email address without `email`, and the domain whitelist needs it. Grant admin consent for your own tenant.
4. **Certificates & secrets → New client secret**; copy the *Value* (shown once) and note its **expiry date**.
5. Copy the **Application (client) ID**.
6. Enable the provider per environment — local in `supabase/.env.local`, staging/production in the dashboard — with **Azure Tenant URL** = `https://login.microsoftonline.com/common`. See [Where provider credentials live](#where-provider-credentials-live-per-environment).

Multi-tenant apps may require one-time **admin consent** from each client organization's IT. Nothing about a client organization is configured in the app registration.

> **The client secret expires** (Entra offers 6 / 12 / 24 months) and all three environments share one app, so a single expiry breaks Microsoft sign-in everywhere at once. The failure is late and confusing: the user authenticates with Microsoft normally, then the callback fails at the token exchange — `AADSTS7000222`, surfaced in the portal as "Unable to exchange external code". Rotate the secret in the app registration and paste the new value into each environment.

### Google

1. Google Cloud Console → **APIs & Services → Credentials → Create OAuth client ID** (configure the consent screen first if prompted). Application type **Web**.
2. Authorized redirect URI = the Supabase callback URL.
3. Enable per environment as above (dashboard: **Authentication → Sign In / Providers → Google**), pasting Client ID + secret.

### GitHub

1. GitHub → **Settings → Developer settings → OAuth Apps → New OAuth App**.
2. Authorization callback URL = the Supabase callback URL.
3. Enable per environment as above (dashboard: **Authentication → Sign In / Providers → GitHub**), pasting Client ID + secret. A GitHub OAuth App allows only **one** callback, so each environment needs its own app.

## Where provider credentials live (per environment)

Local, staging, and production are **three separate Supabase projects, each holding its own copy of every provider credential**. Nothing is shared between them, and — unlike the schema — hosted provider config is *not* in the repo. Where you put a Client ID and secret depends on the tier:

| Environment | Provider config lives in | Applied by |
|---|---|---|
| **Local** | `[auth.external.*]` in `supabase/config.toml` (committed, no secrets) + credentials in `supabase/.env.local` (gitignored) | `env(...)` substitution, read from the **shell** at `supabase start` |
| **Staging** | The staging project's dashboard → **Authentication → Sign In / Providers** | Saved in the dashboard; nothing in the repo |
| **Production** | The production project's dashboard, same page | Same |

The **provider app** (Entra registration, Google Web client) can be a single app serving all three tiers, because it just lists all three callbacks. Only GitHub forces one app per environment. So "three environments" means three sets of *Supabase-side* settings, not necessarily three provider apps.

Two things routinely cost people an hour here:

- **Local Studio (`http://localhost:54323`) has no provider screen.** For local, the config file is the only interface — there is nothing to click.
- **The hosted page was renamed.** It is **Authentication → Sign In / Providers**, not "Providers", at `https://supabase.com/dashboard/project/<project-ref>/auth/providers`. The Microsoft card is listed as **Azure**.

### Local setup

`config.toml` already enables `azure`, `google`, and `github` with `env(...)` substitution, so no secret is committed. Copy `supabase/.env.local.example` to `supabase/.env.local`, fill in the credentials of your *local* provider apps, then **source it before starting the stack** — the CLI reads these from the shell, not from the file:

```bash
set -a; source supabase/.env.local; set +a
supabase stop && npm run db:start     # preserves data; picks up env(...)
```

Verify what the running stack actually enabled — this reads the live GoTrue config, so it distinguishes "enabled" from "enabled and credentialed":

```bash
curl -s http://localhost:54321/auth/v1/settings | grep -o '"azure":[a-z]*'
```

Until a provider's credentials are set, its button appears but errors; email sign-in still works. **A forgotten `set -a; source …` looks exactly like bad credentials** — the provider comes up enabled with an empty client ID, and the provider rejects the redirect.

### ⛔ Never `supabase config push` at staging or production

`config.toml` describes the **local** stack: `site_url` is `http://localhost:5173` and `additional_redirect_urls` is localhost-only. Pushing it to a shared project overwrites that project's Site URL and redirect allowlist, which breaks every magic link and OAuth return on it — including for live clients. Change shared tiers in the dashboard.

## Adding a client domain

The OAuth provider callback is **always the Supabase project's callback** (`…/auth/v1/callback`), never a portal domain. It is fixed **per environment** — local, staging, and production are three separate Supabase projects with three refs, so there are three callbacks — and it never changes when you onboard a client. **Client portal domains never touch the provider apps.**

After auth, Supabase redirects the user back to wherever the portal runs (the `redirectTo` passed to sign-in, which defaults to the current portal URL). That target only has to be in **Supabase's redirect allowlist**:

- **Local** — `supabase/config.toml` → `auth.additional_redirect_urls`, already wildcarded for `http://localhost:5173/**` and `http://127.0.0.1:5173/**`.
- **Staging / production** — the project's **Authentication → URL Configuration → Redirect URLs** in the dashboard (`…/auth/url-configuration`). Not `supabase config push` — see the warning above.

To onboard a new client portal (e.g. `https://hub.acme.com`), add one entry to that environment's redirect allowlist:

```
https://hub.acme.com/**
```

That is the only change — no new provider app, no new callback, no new secret. If clients live on your own subdomains, a single wildcard covers all of them:

```
https://*.disruptcollective.com/**
```

The trailing `/**` matters: it matches any path under the origin, so a redirect back to `/:slug` or a share link resolves. A bare origin (`https://hub.acme.com`) only matches that exact URL.

## Email magic link / OTP

Users can still receive a one-time email link (or OTP code) that signs them in automatically.

## Sign-in flow

```
User enters email
      │
      ▼
check_email_auth RPC (anonymous call)
      │
      ├── 'staff'       → send link immediately  (existing admin/editor profile)
      ├── 'returning'   → send link immediately  (existing member profile)
      ├── 'whitelisted' → send link immediately  (email domain in client's domain_whitelist)
      └── 'unknown'     → show profile form → send link
                              (name, company, country, industry, GDPR consent)
```

The sign-in form is different depending on where the user accesses the app:
- **Root `/`** — Sotto admin sign-in. Only accepts `staff` emails; shows an error for anyone else.
- **Portal `/:slug`** — Client portal sign-in. Accepts anyone; unknown users fill in a profile form to request access.

## Portal context at sign-in

When a user signs in from a client portal (`/:slug`), the portal's `client_id` is embedded in the magic link metadata. If the user is new and their email domain isn't in any domain whitelist, the trigger still assigns the correct `client_id` to their profile based on which portal they signed in from.

## Profile auto-creation

A Postgres trigger (`handle_new_auth_user`) fires on `auth.users` INSERT — i.e., the very first time a user signs in:

1. Reads `name`, `company`, `country`, `industry` from magic link metadata (filled in by unknown users)
2. Checks `clients.domain_whitelist` for the email domain → sets `role = 'member'` and `client_id`
3. Falls back to `client_id` passed in the link metadata (from the portal)
4. If neither matches → `role = 'public'`, `client_id = NULL`

For returning users (subsequent sign-ins), the trigger does **not** fire — their existing profile is unchanged.

## `check_email_auth` RPC

Called anonymously by the sign-in modal to determine which flow to show.

| Result | Meaning |
|---|---|
| `'staff'` | Profile exists with `role = 'editor'` or `'admin'` |
| `'returning'` | Profile exists with `role = 'member'` or `'public'` |
| `'whitelisted'` | No profile yet, but email domain is in a `clients.domain_whitelist` |
| `'unknown'` | No profile, domain not whitelisted — will see the profile form |

## Domain whitelist (automatic member access)

Managed per-client in **Admin → Clients → Edit → Domain whitelist**.

Add a domain like `essteyr.com` to the ESS client → anyone signing in with an `@essteyr.com` address automatically gets:
- `role = 'member'`
- `client_id` pointing to ESS

No admin approval needed — access is instant on first click of the magic link.

## Manual access (no domain match)

For users whose email domain isn't whitelisted:
1. They sign in via the portal and fill in the profile form
2. Profile is created with `role = 'public'`
3. An admin promotes them in the **Users** tab of the admin dashboard

## Supabase configuration

In **Authentication → URL Configuration**:
- **Site URL**: `http://localhost:5173` (dev) / production domain
- **Allowed Redirect URLs**: `http://localhost:5173/**` (dev) / `https://yourdomain.com/**` (prod)

Without the redirect URLs, clicking the magic link shows "Email link is invalid or has expired". The same message also appears when a **corporate mail scanner (Microsoft Safe Links) pre-clicks and consumes the one-time link** before the user does — the fix is to use OAuth (above) for those users, and to run a custom SMTP for deliverability.
