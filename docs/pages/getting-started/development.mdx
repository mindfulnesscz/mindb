# Daily developer routine

This page is the fastest path from a fresh clone to a reviewable contribution. Sotto is one Git monorepo with three runnable applications and one shared release version.

For who owns which fields, see [Platform division](/getting-started/platform-division). For Staging as the shared backend, see [Team staging setup](/getting-started/team-dev-setup).

## 1. Install prerequisites

| Tool | Why it is needed |
|---|---|
| Node.js 22 and npm | Root launcher, desktop/web builds, documentation |
| Rust stable (`rustc`, `cargo`) | Tauri native application and Rust checks |
| Tauri 2 platform prerequisites | Native window/WebView and application bundles |
| Git | Source control and Nextra edit metadata |
| Docker | Local Supabase for migration work only |

Thumbnail rendering needs no separately installed tools. `npm run setup` fetches the bundled engines
(or `npm run deps:native` on its own) — PDFium and LibreOffice, ~290MB download and ~800MB on disk.
See [Thumbnails](/desktop/thumbnails) and [Third-party engines](/reference/third-party-engines).

## 2. Clone and install

```bash
git clone <repository-url> dc-hub
cd dc-hub
npm run setup
```

There is intentionally no root dependency tree. `npm run setup` runs `npm ci` in `desktop`, `web`, and `docs`. Rerun after lockfile changes.

## 3. Configure backends

**Preferred for feature work:** shared Staging — fill `web/apps/client-hub/.env.staging`, then `npm run dev:web:staging`. In the desktop, add a Staging environment (URL + anon key) and sign in as admin/editor.

**Fully local, including assets:**

```bash
cp web/apps/client-hub/.env.local.example web/apps/client-hub/.env.local
# VITE_SUPABASE_URL=http://127.0.0.1:54321
# VITE_SUPABASE_ANON_KEY=<local anon from supabase status>
# VITE_CDN_GATE_URL=http://localhost:8623
# VITE_STREAM_DOMAIN=https://customer-<id>.cloudflarestream.com
npm run db:start
npm run db:reset      # FIRST TIME ONLY — see the warning below
```

### ⛔ `db:reset` destroys local data — local is not scratch space

It drops and reseeds, which wipes
`stream_uid` values for videos already provisioned on Cloudflare Stream, generated thumbnails and page
previews, R2 upload caches, vocabulary, and any tenant configured by hand. None of that comes back from
the seed. The failure then presents as a feature being broken rather than as missing data — a reset that
wiped every `stream_uid` read as a video regression and cost a long hunt in the wrong place.

To pick up new migrations **without** destroying anything:

```bash
npx supabase migration up      # applies pending migrations only
```

Reset only when you actually want a clean slate. The same rule is at the top of `CLAUDE.md`, because
it applies to anyone — human or agent — working in this repository.

Only the anon/publishable key belongs in browser/desktop config. Do **not** put the service-role key or permanent R2 keys in the desktop. Folders and OAuth tokens stay machine-local.

Local dev has its **own pair of R2 buckets** — `dc-hub-dev` (public) and `dc-hub-gated-dev` (private, created 2026-08-03) — which is what honours the rule below rather than working around it. The gated one exists because a public bucket cannot serve the gated tier: public access makes every object a bearer link, the exact thing that tier prevents.

Never mix local Supabase with a shared R2 bucket for pipeline work.

### Gated delivery and video, locally

Both work locally, and neither did before — not because of a design limit, but because four things were never wired up. If gated thumbnails are blank or video says "not provisioned", check these in order:

**Read the symptom first, it narrows this fast.** Every gated IMAGE — the asset thumbnail and all of a
document's page previews — is fetched through the gate. Video comes from Cloudflare Stream and does
not touch it. So:

| Symptom | Where to look |
|---|---|
| Images broken, video plays | The **gate is not running** (`lsof -ti:8623`). `npm run dev` treats it as optional; start it with `npm run dev:gate`. |
| Video dead, images fine | Stream: `stream_uid` on the row, `CF_STREAM_TOKEN`, `VITE_STREAM_DOMAIN` |
| Both dead | Supabase or the environment's config, not either delivery path |

A browser showing broken-image icons with a `net::ERR_CONNECTION_REFUSED` on `:8623` is the first row,
not a bug in whatever you just changed.

1. **`supabase/functions/.env`** needs `R2_GATED_BUCKET=dc-hub-gated-dev`, `R2_GATED_DOMAIN=http://localhost:8623` and `CF_STREAM_TOKEN`. Without the first two, `r2-grant` hands the desktop no gated tier and the pipeline refuses to publish; without the third, `stream-token` and `stream-upload` answer 503 `Video not provisioned` — which reads like "this asset has no video".
2. **The local edge runtime must have been *created* after the functions were added** — created, not started. Its function list is baked into the container's entrypoint when the container is built, even though `supabase/functions/` is bind-mounted, so a function added later answers `404 Function not found` forever. `docker start` brings the stale list back up, and a bare `supabase start` takes an "already running" fast path and skips recreation. Only a full cycle rebuilds it:

   ```bash
   npx supabase stop    # backs up local data by default
   npx supabase start
   ```

   Check what it is actually serving — the list is the first thing it logs:

   ```bash
   docker logs supabase_edge_runtime_dc-hub 2>&1 | head -8
   ```

   A **stopped** runtime looks different and is worth telling apart: Kong cannot resolve the container inside the Docker network, so calls fail with `503 … name resolution failed` rather than 404. Both arrive at the desktop as "CDN steps disabled".
3. **`VITE_CDN_GATE_URL`** must be set, or the portal treats no URL as gated and never requests a cookie — the failure is silent by design.
4. **The gate must be running.** `npm run dev` starts it; `npm run dev:gate` alone.

Why a localhost cookie works at all: the gate's `COOKIE_DOMAIN` is a per-environment var, `localhost` for a local run, and cookies ignore the **port** when deciding same-site — so a cookie set by the gate on `:8623` rides along with an `<img>` on the portal's `:5173`. An ephemeral `*.vercel.app` preview genuinely cannot do this, because a cookie scoped to the real domain is never sent there.

The gate's R2 binding is `remote: true` — the Worker runs locally (its `/auth` route has to reach the local Supabase) while the bucket is the real one. Simulation is not an option: the pipeline uploads through the R2 S3 API, so bytes always land in a real bucket, and a simulated binding would authorize every request correctly and then 404. That needs `wrangler login` and a workers.dev subdomain on the account, so `npm run dev` treats the gate as **optional** — if it cannot start, the other apps keep running and the portal degrades to no gated delivery.

## 4. Start the system

```bash
npm run dev
```

| Label | Command | Address |
|---|---|---|
| `desktop` | Tauri | native window; Vite `localhost:1420` |
| `web` | client-hub | normally `localhost:5173` (default `.env.local`) |
| `docs` | Nextra | `localhost:3001` |
| `gate` | cdn-gate Worker | `localhost:8623` — **optional**, see above |

Focused starts: `npm run dev:desktop`, `npm run dev:web`, `npm run dev:web:staging`, `npm run dev:docs`, `npm run dev:gate`. Port `7623` must be free for Dropbox/Google OAuth and desktop magic-link callbacks; `8623` for the gate.

## 5. Choose the correct change boundary

| Change | Start here | Also review |
|---|---|---|
| Desktop screen / pipeline | `desktop/src/features`, `services` | CDN grant, identity, sync docs |
| Native I/O | `desktop/src-tauri/src` | Tauri capabilities, `check:rust` |
| Naming / filename tags | `desktop/src/domain` | Vocabulary for **filenames**; DB tags admin on web |
| Portal UI / admin | `web/apps/client-hub/src/features` | Platform division, permissions |
| Schema / RLS / RPC | `supabase/migrations` | `db:types` → `@sotto/database` |
| Shared portal rules | `web/packages/asset-library` | Roles: public / member / editor / admin |

Desktop is staff-session privileged under RLS; the web stays anon + session. UI helpers do not replace RLS.

## 6. Feedback loop

1. Pull latest base branch; keep unrelated changes out.
2. Prefer Staging for end-to-end; local only for migrations.
3. Make one coherent change; cover success + empty/failure paths.
4. Update docs when behavior, settings, schema, or operator steps change.
5. Inspect `git diff` for secrets and accidental lockfile churn.

Do not run two pipelines against the same Staging client/source tree at once.

## 7. Testing by area

```bash
npm run check          # version + desktop build + web typecheck + docs + rust
npm test               # desktop Vitest (filename parsing and growing suites)
```

CI (`.github/workflows/check.yml`) runs the same on pull requests.

### Database changes

```bash
supabase migration new <name>
npm run db:reset
npm run db:types       # writes web/packages/database/src/database.types.ts
```

### Documentation

```bash
npm run build:docs
npm run dev:docs
```

## Before opening a pull request

```bash
npm run check
npm test
git status --short
```

Describe the boundary, manual scenarios, schema impact, and screenshots (no client secrets).

## Releasing

```bash
npm run version:patch   # or minor / major
```

See [Versioning and releases](/reference/versioning). Tag `vX.Y.Z` for desktop release CI.
